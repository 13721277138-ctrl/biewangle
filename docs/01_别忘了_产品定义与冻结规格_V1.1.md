# 别忘了_产品定义与冻结规格_V1.1

> **产品名称：** 别忘了  
> **副标题：** 出门带什么，不用脑子记  
> **版本身份：** V1.1｜规格澄清升级，不扩V1功能范围  
> **产品性质：** 场景防遗漏助手 / 场景记忆外挂  
> **目标用户：** 普通成年人，家庭场景强化  
> **V1原则：** Local-first｜Offline-first Core｜无产品账号｜无自动云同步｜无AI依赖｜无远程Analytics  
> **V1.0形成史：** 80问裁决继续作为历史证据；V1.1只修实现歧义、信任边界、内容身份和交付契约。

## 一、产品定义

「别忘了」不是Todo、日历、备忘录，也不是“AI帮你生成一堆清单”。

它解决的是：

> **人在即将出门、旅行、就医、离开酒店、带娃、离家数日等现实场景中，担心“是不是漏了什么”，需要把这份低价值记忆负担交给一个可靠工具。**

核心价值：

> **把脑子里的担心交给工具，然后获得安心。**

核心循环：

> **遇到场景 → 选择高质量模板 → 启动一次真实检查 → 快速确认 / 标记本次不需要 / 补充临时项 → 明确处理关键项 → 诚实结束 → 安心退出。**

V1所有功能都必须服务这个循环。任何功能如果让用户开始“管理这个记忆工具”，而不是减少记忆负担，应默认砍掉、弱化或延期。

## 二、产品信任三原则

### 1、不制造虚假安心

系统只能陈述自己真实知道的状态。

- 有未处理项目，不得显示为全部完成；
- “完成”只表示**当前这份清单快照中的项目全部已处理**，不表示现实世界不存在任何模板外事项；
- 关键项视图只是过滤器，不改变真实完成计算；
- 平台做不到可靠提醒时，不得显示“已设置成功”制造不存在的保证。

### 2、不静默改写事实

- Official Template、Personal Template、Planned Check、Check Run之间只允许显式、单向、可解释地生成或关联；
- 模板更新不得静默改变已经创建的计划或已经开始的检查；
- 官方模板更新不得自动覆盖或合并个人模板；
- 重开一次已经关闭的Check Run，不得无痕抹掉此前的关闭事实。

### 3、不静默丢数据

- 状态操作只有在持久化成功后才算真正成功；
- 允许乐观UI，但写入失败必须回滚或明确显示未保存；
- 刷新、重启、离线、升级、恢复、重置、版本切换都必须优先保护既有数据；
- Local-first不等于“永不丢失”，本地持久化能力和备份是两道不同防线。

产品真正追求：

> **Trust Density = 有效防遗漏与安心增量 / 用户必须付出的操作、配置与管理成本。**

## 三、V1明确不做

- 通用Todo与项目管理；
- 日历替代品；
- 实时多人协作；
- 社交网络、模板社区、关注、点赞、排行榜；
- AI随机生成清单；
- 产品账号体系；
- 自动跨设备 / 跨平台云同步；
- 远程Analytics、广告或第三方行为埋点；
- 游戏化、连续打卡、积分、夸张庆祝；
- 场景变体规则引擎；
- 大型富文本笔记；
- 自由主题装修系统；
- related-template自动联动；
- 为了研究用户而自建复杂本地Analytics子系统。

## 四、正式对象与身份合同

### 1、Official Template

产品内置官方模板，至少具有：

```text
templateId                 永久稳定
contentVersion             官方内容版本
title
applicability
groups[]
items[]
searchAliases[]
featuredOrder?
```

用户可直接使用、收藏、隐藏，但不可破坏原件。

### 2、Personal Template

用户自建或永久修改官方模板后产生的个人资产，至少具有：

```text
personalTemplateId
derivedFromTemplateId?
derivedFromContentVersion?
title
groups[]
items[]
createdAt
updatedAt
deletedAt?
```

来源信息只用于解释，不得用于自动合并官方更新。

### 3、Planned Check

代表一次未来检查意图：

```text
plannedCheckId
status: pending | consumed | canceled
scheduledDate              YYYY-MM-DD，必选
scheduledTime?             HH:mm，可选
createdTimeZoneId          仅作审计 / 提示
sourceTemplateIdentity
plannedTemplateSnapshot    创建计划时冻结
startedCheckRunId?
createdAt
```

硬规则：

- Planned Check创建时冻结完整可启动快照；
- 来源模板之后被编辑、删除或官方升级，不改变该计划快照；
- V1启动计划时默认使用计划创建时的快照，不增加“选旧版 / 新版”步骤；
- 提前开始等同`pending → consumed`；
- `consumed`和`canceled`不再作为未来计划展示，也不继续触发计划提醒。

### 4、Check Run

代表一次真实现实检查，是运行事实的唯一权威实体：

```text
checkRunId
sourceTemplateIdentity
sourcePlannedCheckId?
runTemplateSnapshot
status
items[]
startedAt
lastInteractedAt
closedEvents[]
reopenCount
lastReopenedAt?
deletedAt?
```

Check Run核心业务状态只允许：

```text
inProgress
completed
endedWithUnresolved
discarded
```

以下不是核心状态：

- `planned`：属于Planned Check；
- `reopened`：是事件，重开后状态回到`inProgress`；
- `staleCandidate`：由时间和lastInteractedAt派生；
- `deleted`：属于数据治理。

### 5、History

V1.1不建立第二个会和Check Run争夺事实权的可变History实体。

> **History是已发生Check Run及其关闭事件的只读视图 / 投影。**

规则：

- `runTemplateSnapshot`启动后永久不受模板更新影响；
- 每次关闭追加`closedEvent`，至少记录关闭类型、时间、未处理数、未处理关键项数；
- 在允许纠错的窗口内可以重开；重开只追加事件并回到`inProgress`；
- 超过重开窗口后，不再允许直接修改该Run，只能“基于本次重新开始”生成新的Check Run；
- 若工程为了性能生成物化History记录，该记录只能是派生缓存，不得成为第二个业务事实源。

## 五、检查项语义合同

模板Item至少：

```text
itemId
importance: normal | key
title
condition?
hint?
groupId
sortOrder
```

CheckRunItem至少：

```text
sourceItemId?
state: unchecked | confirmed | notNeeded
oneTimeNote?
runSortOrder
isTemporary
```

硬规则：

1. `notNeeded`只描述本次，不继承到下一次；
2. 本次状态绝不直接改写模板；
3. 本次临时项默认只属于本次；
4. 用户可明确把临时项或本次结果沉淀成个人模板；
5. 官方模板提供关键项默认值，个人模板用户可自由升降；
6. 一个checkbox原则上只代表一个可独立确认事实；
7. `condition`只是适用条件，不自动把项目设成`notNeeded`；
8. 项目主点击只在`unchecked ↔ confirmed`之间切换；
9. `notNeeded`使用明确次级动作，不能通过连续点击三态循环误触进入；
10. 三种状态必须有图形 / 文字 / 可访问名称，不只靠颜色。

## 六、Check Run关闭与重开合同

### 1、真正完成

仅当所有项目均满足：

```text
confirmed OR notNeeded
```

才允许：

```text
status = completed
```

完成页正式文案：

> **这份清单已全部处理**  
> **可以放心出发。**

该文案只针对当前Run快照，不承诺模板穷尽现实事项。

### 2、未解决结束

只要存在`unchecked`而用户仍主动结束：

```text
status = endedWithUnresolved
```

界面：

> **本次检查已结束**  
> **仍有X项未确认，其中Y项为关键项。**

若Y > 0，必须经过明确二次确认路径，但最终决定权仍属于用户。

### 3、丢弃

用户明确选择放弃一次未完成Run时：

```text
status = discarded
```

丢弃不是删除历史记录的同义词。

### 4、重开

`completed`或`endedWithUnresolved`在可调重开窗口内可执行：

```text
reopen event → inProgress
```

必须保留前一次关闭事件并记录：

- `reopenCount`
- `lastReopenedAt`

超过窗口后只允许：

> 基于本次重新开始

### 5、长期未完成

未完成Run绝不自动结束、删除或变成completed。

`isStaleCandidate`仅是派生显示状态：

> 可能已经过期

用户仍可继续、结束或丢弃。

## 七、计划、日期与提醒

### 1、日期 / 时间

- 仅日期计划保存`YYYY-MM-DD`，不转UTC；
- 日期＋时间使用“浮动本地墙上时间”语义：保存`localDate + localTime`，换时区后默认仍显示同一日期和钟点；
- `createdTimeZoneId`只用于审计和设备时区变化时的必要提示，不把个人计划扩展成复杂国际日历系统；
- 过期只是派生状态，不自动结束计划或Run。

### 2、提醒能力梯度

提醒默认关闭，只属于某一次Planned Check。

#### L0｜V1核心

必须实现：

- 首页“接下来”；
- 到期 / 已过计划的应用内提示；
- 用户打开应用时能清楚看到需要处理的计划。

#### L1｜优先增强

平台可靠支持时：

- 允许用户主动加入系统日历 / 导出日历事件。

#### L2｜条件实现，不作为无条件发布硬门

- PWA Web Push；
- 微信订阅消息或其他平台系统通知。

只有在**实施当天当前官方能力、账号条件、权限和必要基础设施均允许可靠实现**时才做。无法可靠实现时必须诚实降级到L0/L1。

#### L3｜明确不属于V1

- 账号化跨设备提醒编排；
- 云同步后的统一提醒中心。

## 八、首页信息架构与确定性排序

首页不是模板库，而是：

> **用户当前的记忆入口。**

优先级：

1. 继续检查；
2. 接下来最多3个Planned Check；
3. 我的常用；
4. 官方精选；
5. 搜索 / 新建。

### “继续检查”只突出一个Run

确定性规则：

1. 优先选择与已经到期 / 最近即将到期Planned Check关联的`inProgress` Run；
2. 若无明显计划优先级，选择`lastInteractedAt`最近的`inProgress` Run；
3. 再以`startedAt`打破平局；
4. 其他inProgress Run必须仍有明确入口可访问。

不得使用AI或不可解释评分。

## 九、开始检查体验

硬目标：

> **打开应用到开始检查 ≤ 10秒。**

默认点击模板直接开始Check Run，不增加：

- 模板预览确认页；
- 启动前裁剪页；
- 必填提醒；
- 必填说明；
- 传统Onboarding。

支持：

- 分组，默认展开；
- 已全部处理组可轻量弱化 / 折叠；
- 全部 / 关键项视图；
- 本次临时加项；
- 本次短备注；
- 本次临时排序；
- 中断恢复；
- 同一模板可存在多个现实Run；
- “继续”必须指向具体Run，不能只凭templateId自动合并两件现实事情。

## 十、模板治理

官方模板：

- 可收藏；
- 可隐藏；
- 不可删除；
- 可直接反复使用；
- 只有发生永久修改时才产生个人副本；
- 官方更新不覆盖、不自动合并个人副本；
- 官方内容身份以`别忘了_官方模板内容库_V1.1.md`为准。

个人模板：

- 可新建；
- 可编辑；
- 可复制；
- 可软删除并恢复；
- 可选择有限图标与系统主题色；
- 不设硬性项目数上限，过长时软提醒；
- 删除个人衍生模板不影响官方模板。

## 十一、搜索

本地搜索，不依赖服务器或AI。

权重：

1. 模板名称；
2. `searchAliases`；
3. 检查项title；
4. 适用说明；
5. hint。

固定验收：

- “护照” → 出国旅行；
- “医保卡” → 住院准备、重要就医；
- “保险箱” → 离开酒店。

## 十二、分享与外发边界

### 1、官方模板

平台允许时可用稳定`templateId`形成平台内深链或网页URL；接收方无需产品账号即可理解内容。

### 2、个人模板

V1优先：

- 可读文本；
- 分享卡 / 图片；
- 复制内容。

无服务器条件下不伪装成长期在线互动链接。

### 3、本次结果

属于独立、显式动作。

默认：

- 不分享`oneTimeNote`；
- 不分享未明确选择的历史信息；
- 不自动带出医疗、行程、家庭等额外个人信息。

分享前应让用户清楚知道将要外发什么。

## 十三、轻量个性化

保持V1结构支持，但**不是P0发布硬门**。

仅在核心Run、数据、备份、迁移、分享和双端语义均稳定后实现。

允许：

- 同一场景多次临时加入同一项 → 建议加入个人模板；
- 同一个人模板某项反复`notNeeded` → 建议考虑移除。

禁止自动删除、自动新增、自动改关键级别、自动改排序。

## 十四、Local-first、持久化与数据耐久性

### 1、本地事实

- 无产品账号；
- PWA与微信小程序默认是两个独立本地数据岛；
- V1不自动同步；
- 微信宿主身份不等于「别忘了」跨端账号。

### 2、持久化成功才是成功

每次勾选、notNeeded、临时项、备注、排序、关闭和重开都必须持久化。

允许乐观UI，但失败必须：

> 回滚或明确标记未保存。

禁止：

> UI看起来成功，底层静默失败。

### 3、PWA持久存储

PWA应：

- 使用可靠本地数据库；
- 支持时检测平台持久存储状态；
- 支持时合理请求平台持久存储；
- 请求失败或平台不支持时正常降级；
- 数据与备份页显示简洁保护状态；
- 不在核心Check Run中弹打扰式教育弹窗。

持久存储不是备份替代。

### 4、用户必须知道的边界

数据页应简洁说明：

- 数据默认只在当前设备 / 当前平台环境；
- 清除站点数据、卸载、重装、设备丢失或换设备可能导致本地数据消失；
- 完整备份是长期保护的重要手段。

## 十五、备份、恢复、迁移与重置

### 1、Backup Envelope

至少：

```text
productId
appVersion
schemaVersion
backupFormatVersion
sourcePlatform
officialContentVersion
exportedAt
data
```

`schemaVersion`描述本地数据结构；`backupFormatVersion`描述导出文件契约，两者独立演进。

### 2、恢复

V1采用整体恢复，不做智能合并。

流程：

> 当前数据保护副本 → 导入临时区 → 解析 → schema / 业务校验 → 全部通过 → 原子提交

失败：

> 当前正式数据不变。

未知未来`backupFormatVersion`或不支持schema：

> 明确拒绝，不冒险解释。

### 3、跨端

两端目标使用相同Backup Envelope语义。

若某平台当前无法可靠完成文件导入：

- 不伪装成已支持跨端恢复；
- 记录在能力矩阵；
- 提供该平台当前最可靠的导出 / 复制能力。

### 4、迁移

正式schema升级：

> 自动保护 → migration → validation → commit

失败保留旧数据。

任何schema变化版本还必须防止：

> 旧客户端与新schema在不兼容状态下并发写同一数据库。

具体协调方案由工程实现选择。

### 5、重置

设置深处提供全部重置：

- 强确认；
- 执行前创建保护副本；
- 官方模板恢复初始状态。

### 6、人类可读导出

PWA优先Markdown/TXT；微信至少提供平台可靠的复制 / 分享文本。

## 十六、可调产品参数

产品语义冻结，以下初始值集中配置，不允许散落魔法数字：

```text
REOPEN_WINDOW_HOURS = 2
STALE_AFTER_HOURS = 24
PERSONALIZATION_MIN_REPEAT = 3
HOME_RECENT_USE_DAYS = 30
```

这些参数可在真实使用后调整，不需要改变schema，也不得改写过去历史事实。

## 十七、视觉与语气

关键词：

> **轻｜干净｜温暖｜安心｜生活感｜成人化｜不管理味**

禁止：

- 满屏红色警报；
- 连续打卡；
- 积分；
- 夸张庆祝；
- 过度卡通；
- 大段说明；
- 密集设置；
- 用颜色作为唯一状态表达。

## 十八、双端原则

最高原则：

> **统一产品，不统一代码；统一行为契约，不统一界面实现。**

### PWA

定位：

> **Mobile-first Use + Desktop-enhanced Management**

要求：

- 手机单手优先；
- Offline-first Core；
- 安装到主屏后完整工作；
- Mac大屏增强模板编辑、历史与数据管理；
- Safari Add to Dock形成独立Web App后真实验收。

### 微信小程序

定位：

> **同一产品的微信原生轻工具版本**

要求：

- 不复制网页导航；
- 更短、更碎片化；
- 原生分享优先；
- 平台能力诚实降级；
- 不为了与PWA表面一致牺牲微信体验。

两端必须通过同一组领域行为合同，但可以使用完全不同UI代码。

## 十九、V1验收四门

### 1、语义门

- 状态机无歧义；
- Planned Check快照稳定；
- Run快照稳定；
- 完成不造假；
- 重开保留关闭事实；
- 双端相同Golden Fixtures得到相同业务结果。

### 2、数据门

- 中断不丢；
- 冷启动不丢；
- 离线核心可用；
- 写入失败可见；
- 备份 / 恢复 / 迁移 / 重置失败不破坏原数据；
- PWA持久存储边界对用户透明。

### 3、交互门

- 新用户不看教程可在约30秒内完成第一次检查；
- 打开到开始检查≤10秒；
- 主操作单手可完成；
- `notNeeded`易理解但不易误触；
- 关键项视图不产生假完成；
- 典型模板目标30—90秒，复杂模板允许更长；
- 核心任务导航深度≤2层。

### 4、真实终端门

- PWA普通浏览器；
- 手机添加到主屏；
- Mac Safari；
- Mac Add to Dock独立Web App；
- 微信开发者工具；
- 微信真机预览；
- 当前账号条件允许时继续推进体验版、审核与发布。

## 二十、发布后停止门：稳定性与价值分开

### 1、稳定性门

至少：

> **约2周＋累计约30次真实Check Run**

覆盖短清单、长清单、空间扫描、高后果模板、计划提前开始、中断恢复、未确认关键项后结束、重开纠错、备份恢复、至少两类真实终端。

期间只修Bug、明显主流程阻碍、数据可靠性 / 兼容性问题。

### 2、价值门

决定普通功能扩张前，人工回答：

1. 相同场景下，用户下次是否愿意再次打开？
2. 使用后是否明显减少“我是不是还漏了什么”的反复回想？
3. 是否发生过模板外的重要遗漏，尤其高后果遗漏？
4. 哪些checkbox让用户不知道该“确认 / 不需要 / 拆分”？
5. 用户是否开始大量配置和管理这个工具，说明产品在Todo化？

> **30次Run证明被使用过，不证明真正产生认知卸载价值。**

V1之后第一优化优先解决：

> **真实使用暴露出的最大信任缺口。**

## 二十一、V1.1范围停止门

V1.1只允许修：

- 产品语义歧义；
- 数据可靠性；
- 官方内容资产身份；
- 平台能力透明度；
- 双端行为一致性；
- 测试与真实交付证据。

不借V1.1新增账号、云同步、AI、模板社区、related templates、更多首发官方模板、复杂Analytics或复杂提醒基础设施。
